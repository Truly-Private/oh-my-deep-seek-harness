# Agent Note: CodeQL 警报处置

Status: implemented

[English](2026-08-16-codeql-alert-dispositions.md) | 中文

## Problem

CodeQL 工作流成功只表示 GitHub 接受了分析结果，并不表示结果中没有警报。把工作流结论当作安全结论，可能让生产代码发现项未经复核；而宽泛的查询排除或无记录的关闭操作，也可能在没有降低风险的情况下让控制面板变绿。

## Decision

下游每次 CodeQL 分析都必须为被分析的精确提交配套一份警报清单。发现项只有在源代码修正后，或在 GitHub 上带有该发现专属说明地完成处置后，才会离开开放清单。配套的 [`security/reviews/`](../../../../security/reviews/2026-08-16-codeql-triage.md) 文件记录数量、警报编号、变更路径、本地检查与仍待补齐的远端证据。

源代码修正在移除被报告的不安全机制时保持既有行为。仓库解析器对不可信文本或仓库规模文本使用有界线性扫描器；生成的 Markdown 与 Mermaid 值先转义反斜杠，再转义各自格式分隔符；profile 初始化使用排他文件创建；JSONL 会话读取通过同一个已打开文件句柄比较 revision。回归测试覆盖畸形长输入、相邻注释、并发 revision 重试与逐字节一致的目录投影。

GitHub 处置只有在报告路径属于测试或 fixture 且不存在生产可达性时，才使用 `used in tests`。`false positive` 必须记录为何查询所建模的安全属性并不存在。`won't fix` 只用于有意提供的可执行代码能力，而且其信任假设与隔离限制已经属于面向用户的约定。工作流通过、位置继承自上游或输入在本地受信任，本身都不足以完成处置。查询套件保持启用，工作流不会通过宽泛排除路径来隐藏已复核发现。

CodeQL 证据不会把 [`security/upstream-lock.json`](../../../../security/upstream-lock.json) 从 `candidate` 改为其他状态。依照[经复核下游接纳决策](2026-08-15-reviewed-downstream-intake.zh.md)，`reviewed` 状态仍要求完整的提交匹配证据与维护者批准。

## Alternatives considered

**只使用工作流结论。** 这只能验证分析结果已送达，不能检查其中的发现，因此不能支撑安全复核声明。

**关闭所有继承发现或本地工具发现。** 来源与执行上下文会影响可利用性，但两者都不能证明发现无害。每条警报都保留自身的源路径与威胁模型说明。

**关闭噪声查询，或排除测试与 vendored 代码。** 这些路径可能包含可执行 fixture、安装行为以及实际随分发产物交付的代码。完整查询集保持启用，精确警报使用窄范围处置。

## Consequences

维护者必须对每个候选提交同时检查工作流结论与 CodeQL 警报 API。控制面板只有在精确风险与信任假设已有记录后，才可保留有意接受的发现；后续源文件移动或可达性变化需要重新复核。这增加了复核成本，但避免把绿色工作流徽章表述成零发现。
