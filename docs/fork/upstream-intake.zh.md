# 经审查的上游接收流程

[English](upstream-intake.md) | 中文

本参考定义 `oh-my-deepseek-harness` 如何接收 DeepSeek Harness 更新。本发行版优先选择已知且经过审查的提交，而不是自动与上游 `master` 同步。

## 信任锚点

[`security/upstream-lock.json`](../../security/upstream-lock.json) 记录精确的主上游 URL、分支、提交与审查状态。它还记录灵感来源仓库，用于署名和设计比较；该仓库不是源代码合并基线。

锁定文件验证器会拒绝未知源 URL、格式错误的提交标识符、不在当前仓库历史中的主源提交，以及缺少提交对应证据的 `reviewed` 状态。

## 接收流程

1. 把 `https://github.com/deepseek-ai/deepseek-harness.git` 获取到 `upstream` remote，且不执行仓库脚本。
2. 从下游默认分支创建审查分支，合并或变基到选定的上游提交，但不发布版本。
3. 更新 `security/upstream-lock.json` 中的主源提交，并把审查状态保持为 `candidate`。
4. 审查从上一个已接受上游提交开始的完整差异，包括工作流文件、安装钩子、包管理器脚本、原生代码、vendored 变更、凭据处理、网络目标与沙箱策略。
5. 运行来源验证、相关仓库测试、CodeQL、依赖审查、秘密扫描与依赖漏洞审计。把任何豁免或受环境阻止的检查记录为例外；无记录不等于通过。
6. 运行本次更新影响的集成路径。只有模型提供方测试不能作为主机智能体桥接证据。
7. 在人工批准且必需检查成功后，把锁定状态设置为 `reviewed`，为精确提交标明证据，并合并审查拉取请求。
8. 仅从锁定文件仍能验证为 `reviewed` 的提交打标签或发布。

## 审查延迟

候选版本审查期间，上游可能继续前进。这是预期行为。安全修复具有更高优先级，但仍保留提交来源与聚焦验证。版本说明必须标明上游提交，让用户无需根据版本名推断就可以比较本发行版与上游。

## 禁止自动合并

发现自动化可以创建 issue 或准备分支，但不能把提交标记为已审查、批准自己的拉取请求、合并、打标签或发布。这些操作需要审查证据与维护者决策。
